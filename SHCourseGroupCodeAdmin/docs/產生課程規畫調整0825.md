- 以 try/catch 包住，不向 UI 拋 Exception

`LoadData()`：

```csharp

```

# 課規產生過程功能按鈕問題處理

## 1. 修改檔案

- `UIForm\frmCreateGPlanMain108.cs`

未改：`GPlanInfo108.cs`、`frmCreateGPlanItemSetup108.cs`、`frmCreateGPlanQueryAndSetup108.cs`、`DataAccess.cs`，以及產生／來源課規／Level／RowIndex 等資料邏輯。

## 2. 原本 `btnCreate_Click()` 為何會提前 `ControlEnable(true)`

`btnCreate_Click` 開頭會 `ControlEnable(false)`。有 INSERT／UPDATE 時會再 `ControlEnable(false)` 並呼叫 `_bgWorker.RunWorkerAsync()` 重新讀取。

`RunWorkerAsync()` 為非同步呼叫，會立即返回。方法最後仍執行 `ControlEnable(true)`，因此 BackgroundWorker 還在 `_bgWorker_DoWork` 時，主畫面功能已被重新啟用。

## 3. `RunWorkerAsync()` 非同步呼叫的影響

啟動後 UI thread 繼續跑完 `btnCreate_Click`。若在 Completed 前就 `ControlEnable(true)`，使用者可再按產生、重新讀取、查詢與設定、操作 DataGrid，甚至對 busy 的 BackgroundWorker 再呼叫 `RunWorkerAsync()` 造成例外。

## 4. 如何透過 `return` 避免產生後過早解鎖

有寫入並啟動重新讀取時：

```csharp
ControlEnable(false);
if (!_bgWorker.IsBusy)
    _bgWorker.RunWorkerAsync();

return;
```

離開 `btnCreate_Click`，不執行方法結尾的 `ControlEnable(true)`。

## 5. `_bgWorker_RunWorkerCompleted()` 作為重新啟用位置

Completed 仍依序：清除並重建 `dgData`、`GPlanDataCount()`、最後 `ControlEnable(true)`。這是產生後重新讀取完成的主要解鎖位置。

## 6. 是否加入 `_bgWorker.IsBusy` 防呆

有。呼叫 `RunWorkerAsync()` 前檢查：

- `frmCreateGPlanMain108_Load`
- `btnCreate_Click` 產生完成後重新讀取
- `btnReload_Click`（busy 時直接 return）

`IsBusy` 為第二層防護，主防護仍是 UI disabled。

## 7. `btnReload_Click` busy 防護

已加入：`if (_bgWorker.IsBusy) return;` 後才 `ControlEnable(false)` 並啟動 Worker。

## 8. `btnCancel` 是否納入 `ControlEnable()`

有納入。產生與重新讀取期間 `btnCancel` 一併 Disabled，完成後再 Enabled。

原因：Worker 執行中關閉 Form，Completed 仍可能操作已釋放的 UI。專案原先未刻意在讀取期間允許關閉，本次一併停用以降低生命週期風險。

## 9–11. 重新讀取期間操作

`ControlEnable(false)` 持續到 Completed：

- `btnCreate` 不可點，不會第二次 UPDATE／INSERT
- `btnQueryAndSet` 不可點，無法進入批次查詢設定
- `dgData` 不可操作（含「設定」）
- `chkStartLevel`、`btnReload` 不可操作

## 13. 其他風險

- 開始級別確認對話方塊仍在 `ControlEnable(false)` 之後；對話期間功能維持停用，與本次「產生過程鎖定」一致。
- 內層 INSERT／UPDATE catch 後若 SQL 清單為空，不會啟動 Worker，會走到結尾解鎖，避免永久 disabled。
- `btnQueryAndSet_Click` 結束仍會自行 `btnQueryAndSet.Enabled = true`，與本次鎖定範圍無關。
