# 課程規劃表合併調整記錄 - 0817

## 修改日期
2026年8月17日

## 修改檔案
`UIForm/frmGPlanConfig108_MergeSubject.cs`

## 原本行為
合併來源課程規畫表時，會將來源 `<Subject>` 複製為 `new XElement(elm)`，依既有規則調整 `Grouping.RowIndex` 後加入目標課規。

合併後的 `<Subject>` **沒有記錄來源課程規畫表名稱**，事後無法從 XML 判斷該科目是從哪一份課規併入。

重複課程代碼檢查方式：
- `TargetCourseCodeList` 只在合併開始時，從目標課規既有 `<Subject>` 收集 `課程代碼`
- 來源科目若 `課程代碼` 已存在於目標課規，則略過
- 新加入的 `課程代碼` **沒有**再寫回 `TargetCourseCodeList`
- 因此若勾選兩份來源課規都含相同 `課程代碼`，兩份都會被加入

## 新的 `來源課規` 行為
每個**本次合併新複製**的 `<Subject>`，在建立 `NewElm` 後立刻寫入屬性：

```xml
<Subject
    課程代碼="A001"
    OfficialSubjectName="國文"
    來源課規="113學年度普通科課程規畫">
    <Grouping RowIndex="..." />
</Subject>
```

規則：
- 屬性名稱：`來源課規`
- 屬性值：目前迴圈中的 `name`（來自 `SelectedGPlanNameList`，即來源課規名稱）
- 不寫死課規名稱
- 只追加屬性，不刪改既有屬性或子節點（`課程代碼`、`OfficialSubjectName`、`Grouping` 等維持不變）
- 目標課規原本已存在的 `<Subject>` **不**自動加上或修改 `來源課規`
- 僅 `RowIndex` 仍依既有合併邏輯調整

## 重複 `CourseCode` 追蹤是否調整
**有調整。** 業務規則確認為：

> 最終合併後的課程規畫表中，同一個課程代碼只應存在一份（可含該課程多個學期 Subject）。

資料模型注意：同一 `課程代碼` 在單一課規內通常對應多個學期 `<Subject>`（共用同一個 `Grouping.RowIndex`）。  
若在每一筆 `NewElm` 產生後立刻執行 `TargetCourseCodeList.Add(CourseCode)`，會讓同一來源課規後續學期列被誤判為重複而漏併。

因此調整方式不是「每加入一筆 Subject 立刻 Add」，而是：

1. 處理單一來源課規時，仍用合併前的 `TargetCourseCodeList` 判斷是否可加入，讓同一來源的多個學期列都能進來
2. 該來源全部處理完後，再把本次接受的 `課程代碼` 登錄進 `TargetCourseCodeList`
3. 後續來源課規若含相同 `課程代碼`，則不再加入

```csharp
HashSet<string> acceptedCourseCodesThisSource = new HashSet<string>();
// ... 同一來源的 Subject 加入 AddSubjectList 時：
acceptedCourseCodesThisSource.Add(CourseCode);

foreach (string code in acceptedCourseCodesThisSource)
{
    if (!TargetCourseCodeList.Contains(code))
        TargetCourseCodeList.Add(code);
}
```

未改動的既有規則：
- 目標課規已有的 `課程代碼` 仍不會被來源覆蓋
- `RowIndex` 計算、`AddSubjectList`、`newRowIndexSet`、`AddSubejctCount`、`GetTargetGPlanInfo()`、`GetAddSubjectCount()` 維持原邏輯

## 測試案例與結果
以與 `btnRun_Click` 相同的 XML 合併演算法進行驗證（專案為 WinForms / FISCA 模組，無法在此環境實際開啟合併畫面）。  
並以 MSBuild Debug 建置專案。

| 測試項目 | 結果 |
|---|---|
| 合併一份來源課規到一份目標課規 | 通過 |
| 每個新加入的 `<Subject>` 都含 `來源課規` | 通過 |
| `來源課規` 等於實際來源課規名稱 | 通過 |
| 合併多份來源課規，各自記錄正確來源 | 通過 |
| 目標課規既有 `<Subject>` 不被改動（不含 `來源課規`） | 通過 |
| 既有 `課程代碼` 重複檢查仍有效 | 通過（目標已有 A001 時，來源 A001 不加入） |
| 兩份來源課規含相同 `CourseCode` | 通過（只保留先勾選來源的學期列） |
| `Grouping.RowIndex` 行為不變 | 通過 |
| `AddSubejctCount` 仍以 unique 新增 RowIndex 組數計算 | 通過 |
| 合併後 XML 結構有效 | 通過 |
| 建置專案無編譯錯誤 | 通過（`SHCourseGroupCodeAdmin -> bin\Debug\SHCourseGroupCodeAdmin.dll`） |

補充驗證：
- 同一來源、同一 `課程代碼` 的多個學期 `<Subject>` 全部保留（若改成每筆立刻 `Add`，只會留下第一學期）
- 來源原始 `RowIndex` 改變時，`LastRowIdx` 仍會加 1
- 兩份來源若原始 `RowIndex` 相同，仍依既有規則可能共用同一個新 `RowIndex`（本次未改此行為）

## 相容性與回歸注意
- 只追加 `來源課規` 屬性，不改既有 XML 結構與 UI
- 目標課規舊資料不會自動補上 `來源課規`
- 讀取課規 XML 的既有程式若只取已知屬性，多一個屬性通常可相容
- 重複課程代碼追蹤從「只對目標既有代碼去重」改為「合併過程中也對已接受的來源代碼去重」；這符合「最終課規同一課程代碼只留一份」的規則，但會改變「兩份來源含相同代碼時兩份都加入」的舊結果
- `RowIndex` / `AddSubejctCount` / 分組邏輯未改
- 建置時僅出現專案原有 warning（MSB3270、未使用變數等），與本次修改無關
